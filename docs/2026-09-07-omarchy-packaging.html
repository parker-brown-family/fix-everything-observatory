▼ ELI5 — tl;dr
💬 comment
💡 Plain English
The observatory is written as a thing you clone into your home directory and run in place — it reads and writes everything next to its own source. Omarchy ships apps as pacman packages that live in a read-only system directory, so the app has to learn the difference between where I am installed and where I keep my stuff. That split is the whole job; everything else is a tarball, a checksum, a build recipe and a pull request. Done looks like pacman -S fix-everything-observatory on a fresh machine, the chip in the bar, the swarm on screen, and pacman -Rns leaving the user's mined history untouched.
▼ Two channels — and this repo is already on the other one
💬 comment
⚠ Read this before anything below
Omarchy has two distribution channels with two checklists, and this repository has already shipped down one of them. omarchyplugins.com takes shell plugins installed with omarchy plugin add from a git URL, listed against a pinned commit. omarchyapps.com lists pacman packages built by omacom/omarchy-pkgs and installed with pacman -S. The develop checklist Parker pointed at is the second one. Everything the repository has done so far is the first one.

💬 comment
⚠ The published README promises the opposite of what the package checklist requires
The plugin checklist asks for removal instructions and no configuration overwrites, and a state move satisfies both — so this is not two rulebooks in conflict. What is in conflict is what the shipped README already promises. README.md:34 says everything the app writes stays inside its own plugin directory, and README.md:37 says to remove it "the same way it came, mined data and all". The package checklist requires the reverse: uninstall must remove packaged files without deleting user data. Both README sentences are published at the pinned commit. The cost of the state move winning later is therefore a reword and one refresh cycle with a stale sentence in the window — not a broken promise to the marketplace, and not a blocker. It remains the sharpest form of the two-channel question, because answering it is choosing where the mined history lives.
💬 comment
⚠ Three things the XDG move would falsify, two of them already published
  • README.md:34 — "everything it writes stays inside its own plugin directory (data/)". Becomes false. The sentence after it, that no user configuration is modified, stays true.
  • README.md:37 — "Remove it the same way it came, mined data and all". Becomes false in the direction the package checklist actually wants, which is the awkward part: the new behaviour is better and the old sentence is what has to change. Write its replacement as the feature it is — the mined history survives a reinstall, it lives at a named path, and here is the one command that removes it — rather than as an apology for the promise it retires.
  • The marketplace submission repeats both in its maintainer notes. It has posted, on Parker's explicit go with the second-channel framing in front of him, pinned at the release-rig commit.
  • BarWidget.qml:56 — the widget resolves its launcher as pluginDir + "bin/fix-everything-observatory", from Qt.resolvedUrl("."). A package layout that installs the launcher to /usr/bin and the widget somewhere else breaks that pointer, silently, at click time.
💬 comment
A published listing does not follow the repository
The marketplace pins an exact commit and serves that snapshot until someone asks for a new one — the failure that had a sibling plugin serving a stale preview through an entire version. The submission has posted, so this is now the live order of operations rather than a choice: if the state move ships, the listing keeps serving the two README sentences above until a refresh is requested by hand. That refresh is a verify-and-publish issue against the marketplace naming the plugin, its id and the new version. The one thing that makes this safe is mechanical — bin/check-listing compares the pinned commit against the newest tag, so tagging v0.2.0 is itself the reminder. Nothing here needs remembering; it needs the reword written into the same change as the state move.
💬 comment
The case for carrying both, and the cost
flea does exactly this — a quickshell app that is also a package in the tree. The package is what makes the app installable, updatable and removable by the same machinery as everything else on the system, and it is the only path for a user who wants the instrument without the bar chip. The cost is two version pins, two staleness surfaces and two places a release has to land. If only one channel is wanted, the plugin is the one already working, and this document becomes a decision to close rather than a plan to run.
▼ What the checklist actually demands
💬 comment
Where the rules live
The develop checklist at omarchyapps.com is the human-readable half. The machine half is the repository it points at — omacom/omarchy-pkgs, default branch master, 100+ packages under pkgbuilds/, each one a directory holding a PKGBUILD and an .omarchy/package.json. It is a build system, not a listing site: it pulls sources, builds in a container for x86_64 and aarch64, signs, and syncs to a pacman repo through three channels (edge → rc → stable).

Three packages already in that tree are close enough to copy from, and reading them is worth more than reading the checklist twice:

PackageWhy it is the model
link-studio The closest analogue by a distance. A local (non-AUR) Python application, installed with python -m installer, shipping a .desktop, docs and licence by hand, and tracked by an upstream block in its metadata that watches a GitHub release feed for a SHA256SUMS file. The rules that will actually catch us, in the checklist's own terms: executables under /opt or the standard paths, no hardcoded usernames, home directories or build paths, cryptographic checksums on every downloaded asset, a valid .desktop entry with icons in standard locations, namcap clean, uninstall removes packaged files without deleting user data, keep the download small, and a pull request that discloses limitations, unusual permissions and required accounts.

▼ The one structural blocker
💬 comment
⚠ The app writes into its own install directory
Every path in the program is derived from where the source file sits, and most of them are writes. Under a pacman install that directory is owned by root and mounted for reading. Nothing else on this list matters until this is fixed, and no amount of PKGBUILD cleverness works around it. 
observatory.py:41   ROOT = Path(__file__).resolve().parent
observatory.py:42   DATA = ROOT / "data"          # manifest.json, manifest.js, http-cache.json
observatory.py:43   CACHE_PATH = DATA / "http-cache.json"
observatory.py:50   SEED_DIR = ROOT / "seed"      # read-only at runtime, written by --seed
observatory.py:605  DATA / f"agent-report-{number}.md"
observatory.py:750  DATA / f"agent-prompt-{number}.md"
observatory.py:860  handler = functools.partial(QuietHandler, directory=str(ROOT))

The fix is the ordinary XDG split, and it is a small change with a large blast radius:

Program, page, icons, seedROOT//opt/fix-everything-observatory/ — read-only, root-owned
Mined manifest, HTTP cache, logsROOT/data/${XDG_STATE_HOME:-~/.local/state}/fix-everything-observatory/

💬 comment
A rule we get for nothing
"Uninstall must remove packaged files without deleting user data" is a requirement we would otherwise have to think about. Once state lives under the user's own state directory, pacman -Rns cannot touch it even by accident, and a reinstall finds the mined history exactly where it left it.
💬 comment
⚠ --seed is a maintainer verb, not a user verb
write_seed() freezes the mined manifest into seed/manifest.js.gz — a write into the install tree. On a packaged copy it will fail with a permission error at the worst moment. It should refuse early and say why, or be hidden from the packaged entrypoint entirely, since the only person who runs it is whoever is cutting a release.

▼ The PKGBUILD, drafted

Modelled on link-studio and herdr. This is the artefact the pull request is mostly made of, and writing it now is what turns the rest of this document into a checklist.

Superseded on 2026-09-08: the one-click agent allocation this plan assumed was removed entirely in 0.2.0, under a marketplace security review. The plugin starts no process beyond its own server, so the three agent-related optdepends (claude-code and two terminals) are gone, the disclosure about spawning an agent goes with them, and the risk note below no longer counts an agent spawn among what the path split touches. The rest of this document records the 2026-09-07 packaging plan as it stood, and that plan is parked.

# Maintainer: Parker Brown <parker@brownfamilysports.com>

pkgname=fix-everything-observatory
pkgver=0.1.0
pkgrel=1
pkgdesc='Live visualizer for the Omarchy repair swarm — tickets, PRs and the agents that open them'
arch=('any')
url='https://github.com/parker-brown-family/fix-everything-observatory'
license=('MIT')
depends=('python' 'bash' 'xdg-utils' 'hicolor-icon-theme')
optdepends=(
  'github-cli: authenticated mining — 5,000 API requests an hour instead of 60'
)
options=('!debug')

source=("$pkgname-$pkgver.tar.gz::$url/releases/download/v$pkgver/$pkgname-$pkgver.tar.gz")
sha256sums=('SET-FROM-THE-RELEASE-SHA256SUMS')

package() {
  cd "$pkgname-$pkgver"

  install -Dm755 observatory.py "$pkgdir/opt/$pkgname/observatory.py"
  install -Dm755 bin/fix-everything-observatory "$pkgdir/usr/bin/$pkgname"

  install -Dm644 app/swarm.html -t "$pkgdir/opt/$pkgname/app"
  install -Dm644 app/*.svg app/*.png -t "$pkgdir/opt/$pkgname/app"
  install -Dm644 seed/manifest.js.gz seed/manifest.meta.json -t "$pkgdir/opt/$pkgname/seed"

  install -Dm644 packaging/$pkgname.desktop \
    "$pkgdir/usr/share/applications/$pkgname.desktop"
  install -Dm644 packaging/icons/256.png \
    "$pkgdir/usr/share/icons/hicolor/256x256/apps/$pkgname.png"
  install -Dm644 app/omarchy-spiral.svg \
    "$pkgdir/usr/share/icons/hicolor/scalable/apps/$pkgname.svg"

  install -Dm644 LICENSE "$pkgdir/usr/share/licenses/$pkgname/LICENSE"
  install -Dm644 README.md "$pkgdir/usr/share/doc/$pkgname/README.md"
  install -Dm644 contract/omarchy-fix-event-v1.md -t "$pkgdir/usr/share/doc/$pkgname"
}
💬 comment
The launcher stops deriving its own root
bin/fix-everything-observatory currently computes ROOT from its own location, which lands on /usr once it is installed to /usr/bin. It needs an install prefix it can be told about — a default of /opt/fix-everything-observatory, overridable by an environment variable so a git checkout still runs in place for development. Its install subcommand, which writes the home-path .desktop, becomes dead weight the moment the package owns that file.
▼ Submission mechanics
  • Fork omacom/omarchy-pkgs and branch off master.
  • Scaffold the package directory rather than hand-rolling it, so the metadata matches what their tooling expects.
  • Write the PKGBUILD, and the metadata block that tells the build system how to track our releases.
  • Run the local build and the inspection gauntlet before opening anything.
  • Open one pull request carrying the package directory and nothing else.
bin/add-package fix-everything-observatory --local --scaffold

That writes pkgbuilds/fix-everything-observatory/.omarchy/package.json. Following link-studio, it should end up as:

{
  "source": "local",
  "upstream": {
    "github": "parker-brown-family/fix-everything-observatory",
    "checksums": "SHA256SUMS",
    "assets": {
      "any": "fix-everything-observatory-{pkgver}.tar.gz"
    }
  }
}
💬 comment
This is the answer to "how will you track updates"
Their pull request template asks how the package stays current. The upstream block is the answer: their check-versions timer watches our GitHub releases on a five-minute tick, reads the digest out of our SHA256SUMS, and bumps the package without a human. It also means our release discipline becomes their release discipline — a release published without a matching checksums file fails their sync rather than shipping something unverified. Their min_release_age option can hold a new release in quarantine for a day if we want a window to withdraw a bad one.

▼ Implementation tickets
💬 comment
T-001
Split the install root from the state directory
done
Shipped
Landed on the plugin track, for its own sake rather than as packaging preparation: until now a reinstall or an upgrade took the mined history with it, which for an instrument whose whole value accumulates was a real loss. The mined history now lives under $XDG_STATE_HOME, the handler routes /data/ explicitly, a one-time migration carries an existing in-tree history across without deleting it, and --seed refuses on a read-only copy instead of failing at the write. Verified against a genuinely read-only install with state elsewhere — the shape a package produces, and one nothing had tested before.
Intent
Teach the program the difference between where it is installed and where it keeps what it mines, so it can live in a root-owned directory.
Touches
observatory.py (ROOT, DATA, CACHE_PATH, SEED_DIR, the three mkdir sites, the two agent-file paths, the server's serve root)
bin/fix-everything-observatory
Acceptance
Given the program installed read-only under /opt
When a user runs the launcher and the first mine completes
Then the manifest, cache and logs are written under the user's state directory
And nothing under /opt has been modified
And a git checkout run in place still behaves exactly as it does today
Gotcha
The seed interception is safe — it matches on the URL string /data/manifest.js and reads the gzip out of SEED_DIR, so it follows the move for free. The path underneath it does not. The branch only fires while no real manifest.js exists; otherwise the request falls through to super().do_GET(), which resolves it against directory=ROOT. Getting the move wrong therefore has two distinct symptoms, and someone who only knows one of them will misread the other as an unrelated bug:
Failure one — the 404
The state directory moves, the mine writes there successfully, and nothing routes /data/. The seed branch stops firing because DATA/manifest.js now exists; the fall-through looks under ROOT/data/, which is not there, and 404s. The page's onerror at app/swarm.html:417 removes the script and retries, so the instrument holds whatever it last had or sits on the empty overlay. This is what a tester of the post-split build actually sees.
Failure two — the silent stale seed
The state directory does not move, so writes into a read-only install root fail, DATA/manifest.js never appears, and the seed branch fires on every request forever. The instrument looks populated and healthy while discarding every cycle it mines. This is the one that ships.
Verification
chmod -R a-w a copy of the tree, run it from there, confirm a full mine completes, and then confirm the page is showing the mined manifest rather than the seed. Both failures pass the obvious check — a populated instrument on screen — so the check has to name which manifest it is looking at.
Preserve
A token-less cycle now writes nothing when a complete seed exists, so an unauthenticated install serves the seed indefinitely instead of degrading to a 300-artifact slice. Both that guard and the seed check are written against DATA, so they follow it on their own — provided neither grows a literal path during the move.

▼ Tradeoffs and what this plan does not do
💬 comment
No AUR package first
Roughly half their tree is source: "aur" — a thin wrapper over a package that already exists on the AUR. Going straight to local skips maintaining a second package in a second place, and puts the PKGBUILD in the repository where their build system can see it. The cost is that people outside Omarchy have no way to install this, which is fine for an app whose whole subject is Omarchy.
💬 comment
No background service, no timer
The repository has a systemd/ directory and packages that use it. Mining on a timer so the manifest is always warm is tempting and would dissolve the cold-start problem entirely. It is also a daemon making authenticated API calls on a user's behalf without them watching, which is a much larger thing to ask a reviewer to accept on a first submission. The launcher's start-on-demand model stays.
💬 comment
Keeping the long name
fix-everything-observatory is lowercase, descriptive and valid under Arch conventions, but it is longer than anything else in their tree and it is what a user has to type. Shortening it is free right now and expensive after the first release, since a rename then needs replaces and conflicts entries forever.
▼ Where this bites
💬 comment💬 comment💬 comment💬 comment
FileRisk
observatory.py Highest. The path split touches the miner, the server and the seed fallback. The seed work has landed and cleared the way, but the failure mode it leaves behind is the quiet one: a packaged install that serves a stale seed forever and throws away everything it mines, while looking entirely healthy.
bin/fix-everything-observatory High. It is the contract every other surface calls — the bar chip, the desktop entry, a keybind, a shell. Changing how it finds its root changes all of them at once, and it is also the file that currently writes the offending desktop entry.
The installed .desktop on this machine Medium, and sneaky. The user-level entry pointing into the working tree outranks a packaged system entry, so the app can appear to work after install while actually still running from the checkout. Every test result is suspect until it is removed.
seed/manifest.js.gz Medium. It dominates the package size, it is generated by a command that writes into the install tree, and it goes stale on a schedule nobody set. Whatever is decided about it should be decided once and written down.

Question 1
Does the 1.2 MB seed ship inside the package, or get fetched on first run?
Shipping it is simpler and makes the app work offline out of the box, at the cost of a package that is 95% frozen data and a checklist line that says to keep the download small. Fetching it needs a second checksummed source and a story for an offline machine. My read is ship it and spend one sentence in the pull request justifying it, but the reviewer may disagree and it is cheaper to have the answer ready.

Question 2 — the one that decides whether the rest of this happens
The plugin ships and works. Do we want the pacman package as well?
This plan was written against the apps checklist, and while it was being written the repository finished the plugin track instead — tagged, released, gated, CI'd, with a marketplace submission drafted and waiting on your word. The package buys three things the plugin does not: installation by the same machinery as everything else on the system, a user who wants the instrument without the bar chip, and a listing on omarchyapps.com. It costs two version pins, two staleness surfaces, and a coexistence problem that is quiet rather than loud when it goes wrong. flea carries both, so it is clearly doable. What keeps this urgent is that the answer decides where the mined history lives — the first ticket in this document, and two sentences in a README that is now published at a pinned commit. The submission posted before this could be weighed, which costs a reword and one refresh cycle rather than anything structural. My read: worth doing, and the state move should carry the README reword and the listing refresh in the same change rather than trailing them.

Question 3
Is fix-everything-observatory the name we want a user to type, forever?
It is valid and it is descriptive. It is also 26 characters and longer than anything else in their tree. The first published release fixes it: after that a rename needs permanent replaces and conflicts entries so existing installs upgrade cleanly. Now is the only cheap moment to change it.

Question 4 — answered while this was being written
Does the path split wait for the cold-start work? No. It landed, and it rebases cleanly.
The seed work shipped as the commit that gives a fresh clone a full instrument, and it makes no write assumption anywhere near the install root: the serving path only reads the gzip and its sidecar, and the one writer is the maintainer-only freeze command, which should fail on a packaged copy. Both the seed check and the slice guard are written against the data constant, so they follow it to a state directory on their own. The one thing that does not follow it is the fall-through underneath the seed branch, which is now the gotcha on the first ticket.
